# Opportunity follow-through and relationship outcomes

## Implemented contract

The slice records two independent append-only histories for an exact owner, recipient, Opportunity, source family, and occurrence cycle. Action reports support `unknown`, `planned`, `user_reported_completed`, `not_completed`, `dismissed`, and `no_longer_relevant`. Relationship outcomes support `unknown`, `went_well`, `went_poorly`, `appreciated`, and `unnecessary`.

Every record is an explicit owner report with server-resolved `brain_execution` lineage and server receipt time. The client cannot submit owner identity, relationship identity, source identity, evidence, provenance, verification level, authoritative time, or confidence. There is no supported system-observed or externally verified completion level; such payloads are rejected. Clicks, links, exposure, persisted card state, dismissal, elapsed time, silence, and recommendation disappearance do not prove action or outcome.

Action and outcome use separate lineages. Correction appends a successor version. Withdrawal appends an inactive head and retains all prior records. Historical setters and withdrawals resolve every identity and provenance field from an owned stored event even when the current Opportunity has disappeared; they never resolve against a later recurrence. The expected version belongs to the target dimension, so an action event can anchor the first outcome at version zero. Fingerprinted receipts include anchor, dimension, value, and version, making exact retries inert while changed reuse conflicts; event and receipt writes are atomic. Optimistic versions reject stale changes and wrapped PostgreSQL unique violations map to conflict.

`already_handled` remains the original explicit feedback event. The workspace reads it through a linked projection; it is not copied, renamed, or upgraded to verified completion, and its existing feedback withdrawal controls remain authoritative.

## Product projection

The production Concierge route supplies the PostgreSQL adapter. The builder loads temporal history, then explicit feedback, then follow-through history before fatigue and delivery. A follow-through read failure fails closed. Only the exact current occurrence with `user_reported_completed` or `no_longer_relevant`, plus the compatible active exact-occurrence `already_handled` owner report, is restrained. A later recurrence, another recipient, another Opportunity, and null occurrence identity remain distinct. Planning, noncompletion, dismissal, relationship outcome, clicks, and passive presentation do not suppress.

The Concierge provides compact action and outcome selects, pending/success/uncertain states, stable retry keys, progressively disclosed retained correction and later-outcome controls, and withdrawal after suppression or source disappearance. It does not create tasks, deadlines, rank changes, cap changes, or external verification claims.
